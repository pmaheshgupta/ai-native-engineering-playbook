Enterprise Agentic AI Platform

Configurability

As of 2 November 2026 · Mahesh Gupta

Every organisation has different needs, processes and existing tools, so the platform keeps a small fixed core and makes everything else optional or swappable. If the platform assumes one way of working, teams either bend to it or work around it, and workarounds become shadow AI.

Three rules follow:

  1. Fix the contract, not the product. The core defines what every call and every agent must carry; any tool that honours it can plug in.

  2. Plug in through open standards, never through proprietary APIs, so an organisation can bring its own tools.

  3. Treat processes as configuration. Tiers, approvers and target times are settings each organisation edits, not code.

The dashed lines are plug-in points: any tool that speaks the slot's open standard and honours the core contract can replace the platform's default.

The fixed core

Four things cannot be optional because they hold every other part together. Even these can be the organisation's own product, as long as it honours the contract.

Core componentWhy it can't be optionalCan they bring their own?
Registry of agents, models and toolsWithout one inventory, nobody can govern, cost or secure what they can't seeYes, if it exposes the inventory through an API and accepts A2A Agent Cards
Agent identityEvery action must trace to an agent and the user it acted forYes: Entra, Okta or another identity provider that issues per-agent identities
One enforcement pointPolicy, routing and cost tags need a single place to applyYes: an existing gateway such as Kong or Apigee, if it applies the tags and policies
Telemetry and audit contractCost, quality, security and compliance views all read the same recordsYes: any backend that receives OpenTelemetry

The contract any bring-your-own component must honour:

  1. Every model, tool and agent call carries four tags: agent ID, owner, use case and cost centre.

  2. Every call emits an OpenTelemetry GenAI trace with one trace ID across hops.

  3. Every agent, model and tool is registered with an owner and a risk tier before use.

  4. Every call is checked against the central policy decision before it runs.

  5. Audit records are tamper-evident and exportable.

Processes as configuration

The tiers, approvers and RACI in Operating processes are defaults. Each organisation can change:

  1. The number of risk tiers and what puts work in each.

  2. Who approves each process at each tier.

  3. Target times and when a request escalates.

  4. Which processes are switched on at all.

  5. RACI roles, mapped to the organisation's own job titles.

  6. Thresholds: budget caps, eval pass marks, how long access lasts before recertification.

How: approval chains live as versioned workflow definitions, and runtime decisions (may this agent call that tool?) live as policy as code, for example in OPA or Cedar. Changes to the configuration go through approval and audit like any other change.

Configuration by level

Settings flow down from the platform contract to the organisation, then to each line of business (LOB), team and agent. Each level can tighten what it inherits but never loosen it: a team can demand a higher eval pass mark than the organisation, never a lower one. Loosening needs a time-limited exception (below).

Never below organisation level

One team getting these wrong affects everyone, so they stay with the organisation:

  • Risk tier definitions and data classes.

  • Mandatory guardrails and the kill switch.

  • The identity model and the four tags.

  • The approved vendor and model list.

  • Minimum log retention and data residency.

Sandbox and exceptions

  • Sandbox: with synthetic data only, teams can try models outside the catalogue, skip approvals and spend a small experiment budget; nothing reaches real data or production.

  • Exceptions: a team that needs to loosen a setting raises a request with an owner, a reason and an expiry date. The CISO and the LOB head see every open exception, so none quietly becomes permanent.

Onboarding questionnaire

Eight questions recommend a profile and show which modules are on, off or replaced by the organisation's own tools. The answers also give the delivery manager a clear scope.

  1. Which regulations apply: EU AI Act, India DPDP, RBI, SEBI, IRDAI, HIPAA, others?

  2. Will agents only advise people, or also take actions? Can any action move money or affect a person's rights?

  3. Which data classes will AI touch: public, internal, confidential, personal, restricted?

  4. What is already in place: gateway, identity provider, observability, ITSM, GRC, DLP, FinOps tools?

  5. Which clouds and model providers are approved? Must data stay in-country?

  6. How many teams or business units in year one? Will you serve outside clients?

  7. Who approves changes today: a change board, a risk committee, team leads?

  8. What usage and budget do you expect in the first year?

Traps to avoid

  • Building every module yourself. The value is the core contract and the glue; buy or reuse the rest.

  • Making the platform one more silo. If it can't read the organisation's existing tools, teams will route around it.

  • Hard-coding one organisation's process. The next organisation will need a different approval chain.

  • Letting a bring-your-own tool skip the contract. A gateway that doesn't apply the four tags breaks cost, audit and security views for everyone.

Open decision: whether the platform serves one organisation or many. Serving many means more investment in tenancy, configurability and connectors; serving one means more depth in that organisation's own processes.
