Enterprise Agentic AI Platform

Agentic AI Platform Stakeholder Map

As of 2 November 2026 · Mahesh Gupta

Summary

An enterprise agentic AI platform has five stakeholder layers, and each one needs a different surface on the same platform: the board sees value and risk, finance sees cost per outcome, IT and security see a control plane, builders see an SDK, and the business sees agents inside the tools it already uses.

Scope: the platform covers agents and the LLMs, prompts, tools and data they use. Classical machine learning (model training, feature stores, forecasting and fraud models) stays on the ML or data platform; this platform integrates with it rather than replacing it.

  • Strategy — CEO and board. Set the AI ambition, fund it, and own the outcome.

  • Governance and control — CFO, CIO/CTO, Chief AI or Data Officer, CISO, Chief Risk Officer and General Counsel. Set budgets, standards, policies and risk appetite. Below them, VPs, delivery and programme managers turn that policy into staffed, delivered and measured work.

  • Platform and operations — platform engineering, MLOps/LLMOps, data engineering, FinOps, security operations, SRE. Run the shared infrastructure.

  • Builders — AI engineers, application developers, data scientists, QA/evaluation engineers, product managers. Turn models into agents and apps.

  • Consumers — business units, citizen developers, employees, customers and partners. Use what is built and generate the value (and the cost).

The 2026 market has reorganised around this split. Hyperscalers and model labs now sell agent platforms with a management control plane, and separate tool categories have matured for governance, AI FinOps, runtime security and observability. Your platform wins by giving every layer its own view of one shared inventory of models, agents, data and spend.

What the numbers say executives are worried about:

  • Return. Gartner found 74% of CIOs report AI implementation costs break even with, or exceed, realised benefits.

  • Governance gap. Only 34% of organisations have well-defined AI governance structures (Gartner, 2026). Gartner expects AI governance platform spending to reach $492M in 2026 and pass $1B by 2030.

  • Cost. 98% of FinOps practitioners now manage AI spend, up from 31% in 2024.

  • Security. Enterprises spent $49B on AI-powered security tools in 2025 but $2.8B securing AI itself (Gartner); on average only 47% of an organisation's agents are monitored or secured.

Why this layer needs its own view:

  • The productivity question is unresolved. DORA's 2026 report on AI-assisted development describes an initial productivity dip, partly a "verification tax" of reviewing generated code; 84% of 600+ engineering leaders call productivity a top concern and 60% say they need better data (Jellyfish, May 2026).

  • Review becomes the bottleneck. LinearB's 2026 benchmarks are reported to show AI-assisted pull requests waiting about 2.5 times longer for review, which engineering managers need to see and fix.

  • Status reporting is still manual. 72% of organisations spend half a day or more each month collating project status, which is the first job delivery managers hand to agents.

The review adds one module for this layer: 16 Delivery and engineering analytics, which joins AI usage and cost with delivery metrics (DORA, cycle time, review wait) and project status, so VPs and delivery managers see AI's effect on delivery, not just usage.

Three signals for this layer:

  • MCP is now the default integration layer, and its own 2026 roadmap names audit trails, enterprise sign-on and gateway patterns as the gaps still being closed. Build the gateway yourself or buy it; don't let teams wire tools to agents directly.

  • Gartner's 2026 governance hype cycle puts LLM observability, AI runtime defence, monitoring as code and eval-driven development under one operational theme: governance is enforced at runtime, not in a policy document.

  • Context is the common failure point. The same report traces many AI failures to poor grounding and unmanaged knowledge, which makes the data team a first-class platform stakeholder.

Agent-to-agent communication, discovery, authorization and compliance

These four controls decide whether agents from different teams and vendors can safely work together. Open standards now exist for the first three: A2A for agent-to-agent calls, signed Agent Cards for discovery, and OAuth token exchange for authorization. Compliance frameworks converge on the same four demands: identity, least privilege, audit logs and human oversight.

The calling agent never holds the user's original token: the gateway swaps it for a narrow token that names both the user and the agent, pauses for a human on risky actions, and logs every hop before the call reaches the remote agent.

Compliance requirements an agent platform should meet, whichever framework applies:

  1. Inventory. Every agent is registered with an owner, purpose, risk tier and version.

  2. Identity binding. Every action is traceable to the agent and to the user it acted for.

  3. Least privilege. Scoped, short-lived tokens; no standing access; access revoked when the task ends.

  4. Audit trail. Tamper-evident logs per trace, not per request, kept for the retention period each regulation sets.

  5. Human oversight scaled to autonomy. Drafts need review; irreversible or high-value actions need explicit approval.

  6. Change control. Prompts, models, tools and Agent Cards are versioned; nothing is edited live without a record.

  7. Monitoring and incidents. Continuous checks on behaviour, plus an incident-reporting workflow.

  8. Data protection. Purpose limitation, consent and cross-border rules (DPDP in India, GDPR in the EU) applied to what agents read and pass on.

The Agent Card itself is an attack surface: anyone who can rewrite it can redirect callers or plant prompt-injection text. Accept only signed cards from your own registry.

Core platform components

The doc named the gateway but not the components most requirements land on. Four were asked for (LLM gateway, data classification, prompt hub, metrics and observability); the persona review found nine more. Each gets requirement statements below; owners match the stakeholder matrix.

LLM gateway

The model-facing half of the AI gateway: one API to every approved model. Datadog data shows about 2% of LLM calls errored in early 2026, with rate limits behind roughly a third, which is why routing and fallback belong here. Owner: platform engineering. Products: LiteLLM, Portkey, Kong AI Gateway, Cloudflare AI Gateway, Bifrost, Databricks Unity AI Gateway.

  1. It must expose one OpenAI-compatible API for every approved model, cloud or self-hosted.

  2. It must keep provider keys in a vault and issue virtual keys per team, app and agent, each with a budget and rate limit.

  3. It must route by policy (cost, latency, data classification, region) and fall back automatically on errors and rate limits.

  4. It must support provider prompt caching and a semantic cache, with opt-out for sensitive use cases.

  5. It must redact or block classified data before a call leaves for an external provider.

  6. It must emit a trace, token counts and cost tags (agent, owner, use case, cost centre) for every call.

Model catalogue and lifecycle

  1. Every approved model is listed with provider, hosting region, licence, cost, risk rating and allowed data classes.

  2. New models pass the standard eval suite before teams can select them.

  3. Provider deprecation dates are tracked, and affected owners are warned with a tested replacement.

  4. Swapping a model behind an agent triggers regression evals and a change record.

Data classification and DLP

Labels are the foundation: Microsoft's guidance is to have sensitivity labels and DLP live before AI-specific controls, and to start with four to six labels, not twenty. Owner: Chief Data Officer and DPO, enforced by the CISO. Products: Microsoft Purview DSPM for AI (classifies prompts and responses in real time, including ChatGPT, Gemini and Claude use), Nightfall.

  1. A 4–6 level taxonomy (for example public, internal, confidential, restricted, personal) is applied to sources before anything is indexed.

  2. Chunks, embeddings and agent outputs inherit the highest label of the sources they came from.

  3. The gateway checks each label against the model's allowed classes; restricted data goes only to in-region or self-hosted models.

  4. Prompts and responses are classified in real time and masked or blocked by policy.

  5. Retrieval uses the end user's permissions, never the agent's broader access.

  6. Classification events feed the DPO's processing records and the CISO's SIEM.

Prompt hub

A registry that keeps prompts and system instructions out of application code, versioned like software. Owner: LLMOps, with product managers and prompt designers as editors. Products: Langfuse, LangSmith, PromptLayer, Braintrust, W&B Weave, MLflow Prompt Registry.

  1. Each prompt has a name, version, owner and environment label (dev, staging, production).

  2. Every change shows a diff, passes review and an eval run before promotion.

  3. Rollback is instant, and versions can be traffic-split for A/B tests.

  4. Every trace records the prompt version, model and parameters that produced it.

  5. Approved shared fragments (safety instructions, tone, disclaimers) are reused across teams.

  6. Prompts are scanned for secrets and personal data and labelled like any other data asset.

Metrics and observability

OpenTelemetry is the common vocabulary, but its GenAI conventions moved to a separate repository in June 2026 and are still marked Development; they cover model calls, agent steps, MCP spans and token metrics. Owner: LLMOps and SRE. Products: Datadog LLM Observability (supports the conventions natively), Langfuse, Arize, LangSmith, Grafana.

  1. Instrument with OpenTelemetry GenAI conventions, pinned to a version, since they are not yet stable.

  2. One trace ID follows a request across user, agent, A2A hops and MCP tool calls.

  3. Prompt and response content is captured only where the data label allows, redacted otherwise.

  4. A standard metrics catalogue (below) has a named owner and target for each metric.

  5. Alerts cover quality, cost and security, not only uptime.

  6. Traces are retained for the period each regulation sets and can be exported for audit.

Market landscape by stakeholder level

Read top to bottom, policy and budget flow down from strategy to the builders; read bottom to top, usage, cost and value data flow up. The gateway is the one category every other layer depends on, which is why it is first in the build order below.

What this means for your platform

Build one inventory and one gateway first; every stakeholder view is then a query over the same data. Each model call and tool call should carry four tags at the gateway: agent ID, owner, use case and cost centre. Without them, the CFO cannot attribute cost, the CISO cannot trace an action and the CEO cannot see value.

Modules 1–4 are the minimum before any agent reaches production. Modules 5–8 make the platform fundable and auditable. Modules 9–10 scale it to the business and keep executive support. Of the modules the review added, run 12 (data classification) before module 6 indexes anything, and 14 (kill switch) before the first agent reaches production.

How these modules are run day to day (onboarding a line of business or an agent, approving prompt versions, granting agent-to-agent access, incidents) is set out by role and risk tier in Operating processes.

Open questions to settle before design:

  • Which clouds and model providers must you support on day one?

  • Which regulations apply (India only, or EU and sector rules such as RBI, SEBI, IRDAI)?
